# Known issues

Bugs in the compiler, runtime, standard library and tools that are not fixed yet, each with a reproduction. Entries found on 2026-11-16 come from an audit of the commits after `31abf4c` and were checked against `dbc5789`; older entries were last checked against `c92a964` (2026-11-13) or the 2026-11-14 working tree. The structural causes behind many of them, and the plan for them, are in `architecture.md` §12-14.

This file lists bugs only. Deliberate gaps (features that don't exist yet) are in README.md, Known limitations; what changed and what was fixed is in `changelog.md`.

## Adding an issue

A bug found while working on something else is recorded here and not fixed in the same run (CLAUDE.md, Robustness Bar); known issues are fixed in runs of their own. An entry has:
- **What is wrong**, in one sentence, under the heading that matches its effect: wrong results with no error (soundness bugs) first.
- **A reproduction**: the smallest program, what it does, and what it should do.
- **Where it was found**: the date and the work it turned up in, and the cause if known (file and function).
- **Reach**, when a change made it easier to hit: which change, and how.

When a change fixes an issue, delete its entry here and describe the fix under Fixed in `changelog.md`.

## Wrong results with no error

- A float from an untyped value in a vec literal with an int is truncated: `fn id(x) -> x`, then `print(vec [id(2.7), 1])` prints `[2, 1]`; it should be `[2.7, 1.0]` (as `vec [2.7, 1]` is) or an error. Found 2026-11-16 auditing dates; `31abf4c` does the same.
- A native `str` that is a null pointer, on the left of a comparison with a str column cell, crashes: with `extern fn nullstr() str as 'my_nullstr'` (the glue returns `nullptr`), `t | e -> filter(nullstr() == e.name)` makes the binary die with a segmentation fault and `quark run` exit 255 with no message. With the operands swapped, and at `31abf4c`, it is `a native function declared to return str returned a null pointer at ...`. Cause: the default case of `strViewCmp` (`lower/expr.go`) turns the raw `const char*` into a `std::string_view` (`strlen` of a null pointer). Found 2026-11-16 auditing tables v0.2 (65e9988), which introduced it.
- A cached `extern source` object is reused after a header it includes changed, when the edit keeps the header's size and mtime (`touch -r`, `cp -p`, rsync, filesystems with 1-second timestamps): a header changed from `222` to `333` still prints `222`. Only the source itself is hashed by content; the headers it includes are keyed by path, size and mtime (`externObjectKey` → `hashFileStat`, `toolchain/sources.go`). Found 2026-11-16 auditing 11df436; the cache test edits only the `.cpp`.
- `extern include_path` directories are global to the program, so one module's `extern source` compiles against another module's header. Modules `moda/a.qrk` and `modb/b.qrk` each have `extern include_path 'inc'` with their own `inc/cfg/value.h` (`CFG_VERSION` 1 and 2) and an `extern source` that includes `<cfg/value.h>`: a program that imports both prints `1` for `b::version()`, and one that imports only `modb` prints `2`. Found 2026-11-16 auditing 11df436. Reach: header glue already worked this way; 11df436 carries it into separately compiled sources, which could be compiled with their own file's directories plus the command-line ones.
- Two `extern source` files that define the same inline function or class member differently link without an error, and every call uses one of them: two modules' `glue.cpp` each define `inline int64_t Scale::factor()` (returning 10 and 1000), and both modules' calls get 10. In header glue the same code was a compile error (a redefinition in one translation unit). A rule in `specs/ffi_v0_1_spec.md` §2.5 that glue sources keep their helpers in an anonymous namespace (followed by the stdlib glue), or detection (`-Wodr` with LTO), would close it. Found 2026-11-16 auditing 11df436.
- A handle's generation counter is 32 bits (`types/resource.hpp`), so after 2^32 reuses of one slot a closed handle becomes valid again and reads the new handle's payload instead of failing with QK-FFI-004 (reproduced with a create/close loop in glue, about 380 s). A 64-bit generation, or retiring a slot when its generation wraps, would close it. Found 2026-11-16 auditing 11df436.
- A handle kind's close function never runs at program exit, after a normal end or a runtime error, so a native kind that buffers (a compressor, a database transaction) loses its data. Glue whose `wwrite(h, s)` appends to a buffer that the close function writes to the file: `w = wopen('out.txt')`, `wwrite(w, 'hello')`, `print('done')` leaves `out.txt` empty. The docs say only that a kind with a close function is finalized when the handle becomes unreachable. `std/io` is not affected (it writes through unbuffered descriptors). Found 2026-11-16 auditing 11df436.
- `qext::errf` (`ext/api.hpp`) has no printf format attribute, so a wrong argument type compiles without a warning and gives a wrong message, and user text becomes a format string: `qext::errf("%d rows failed", n)` with an `int64_t` 5000000000 gives `705032704 rows failed`, and `qext::errf(user_text)` with a `%s` in the text segfaults. Found 2026-11-16 auditing 11df436.
- In `quark repl`, `sys::exit(0)` or `sys::exit(2)` in an input discards the input silently: nothing is printed, the session goes on, and the input's assignments are lost. Found 2026-11-16 auditing 87a01d1.
- `quark repl` never turns on bracketed paste (it doesn't write `\x1b[?2004h`), so in a terminal a pasted block is read line by line, not as one input (`specs/repl_v0_1_spec.md` §3.6): in the spec's §3.2 rollback example, `n = 2` is committed before the line that fails. Found 2026-11-16 auditing 87a01d1, from the output in a pty.
- Windows `quark repl` (`runtime/repl/host_win.cpp`), found by reading the code on 2026-11-16 and not reproduced (no Windows machine): rollback restores Quark values from a deep copy but not native state (the `std/random` engine, resources), and object identity changes; a stack overflow (`0xC00000FD`) isn't among the codes `filter_code` handles, so it ends the session; an integer divide by zero is reported as an access violation; the Ctrl-C handler moves RIP to `raise_interrupt` without a return address or stack alignment, possibly while a GC or CRT lock is held; every input copies the whole session, including inputs that succeed.
- A vec of between 2^61-8 and 2^61-1 elements overflows the heap: `random::uniform_vec(2305843009213693944)` passes the `SIZE_MAX / 8` check in `random.hpp`, then `n * 8 + 64` wraps in `quark::vec::alloc` (`types/vector.hpp`), a block of 0 to 56 bytes is allocated, and `memset` writes about 2^64 bytes into it (segmentation fault, status 139). One element fewer gives a clean out-of-memory error. The size check belongs in `alloc` itself. Found 2026-11-16 auditing 687a147. Reach: `uniform_vec`, `normal_vec` and `randint_vec` (687a147) reach it with one call.
- `qext::handle_close` on a parent handle is allowed while a child that named it as `parent` is still open. The parent's close function runs and frees its payload; the child stays usable from Quark (`handle_get` on the child succeeds). For a real library object (a DB connection whose native pointer is only valid while the database lives), later use of the child is a use-after-free in native code, with no Quark error. Reproduction: `p = parent(); c = child(p); close(p); print(read_child(c))` prints the child's payload. The parent field only orders GC finalizers (`specs/ffi_v0_1_spec.md` §2.8); it does not reject an explicit close. Found 2026-11-14 reviewing FFI phase 2 (P3). Reach: P3 adds `handle_close` and parents, which SQLite/DuckDB are meant to use.
- `e.col == null` in a query verb is never true, so `filter(e.mpg == null)` returns no rows even when `mpg` has missing values, with no error or warning: with a `tbl[Car]` read from a CSV whose last row has an empty `mpg`, it prints `tbl[Car]: 0 rows`. A comparison with a missing operand is missing (D22), so the missing row's predicate is missing and the row is dropped, and a present value is never equal to `null`; `mutate(z = e.mpg == null)` gives `false` for present rows and `null` for the missing one, and `filter(e.name == n)` with `n = null` likewise. SQL has the same rule (`x = NULL` is unknown), but there `IS NULL` exists; a Quark query has no way to test or replace a missing value (no `is_missing`, no `fillna` on a cell), so the comparison with `null` is what a user writes. It should be a compile-time error that names the way to do it. Found 2026-11-16 probing queries for tables v0.3.

## Fails loudly, but with a C++ error, a wrong location or a misleading message

- A runtime error inside an anonymous function's body is reported at the caller's location: `g = fn(n) -> 1 + to_int('x')`, then `print(g(0))`, says `to_int() cannot parse 'x' as integer at loc.qrk:2:6` (the `print` line), where it should be line 1; a stack overflow through `g = fn(n) -> 1 + g(n)` likewise. The lambda's C++ function (`quark___lambda1`) sets no source location; a `fn f(n) -> ...` declaration's body does. Found 2026-11-16 testing the stack-overflow fix.
- A comparison with a str column cell whose left operand is a raw int, float or bool passes the checker and fails in clang: `filter(1 == e.name)`, `filter(e.id == e.name)`, `filter(e.x != e.name)`, `filter(n == e.name)` with `n = 3`, and `mutate(c = e.id == e.name)` give `no matching function for call to 'q_sv_cmp_val'`. At `31abf4c` they compiled (values of different types compare unequal), and `e.name == e.id` still does. The default case of `strViewCmp` (`lower/expr.go`) passes the other operand unboxed. Found 2026-11-16 auditing tables v0.2 (65e9988), which introduced it; it breaks `specs/tables_v0_2_spec.md`'s promise that a v0.1 program compiles under v0.2.
- In `quark repl`, an extern method declared in one input and called in a later one fails in clang (`use of undeclared identifier 'h1_shout'`): `useForeignThunk` (`lower/calls.go`) skips methods. Found 2026-11-16 auditing 87a01d1.
- `quark repl` ignores `extern source`: `incl './lib'`, where `lib.qrk` has an `extern source`, fails with `input-1.so: undefined symbol: ...` because the sources are never compiled or linked into an input. Found 2026-11-16 auditing 11df436 and 87a01d1.
- `quark repl` doesn't print the type-change warning (`QK-CHECK-002`) when the input succeeds, since diagnostics are printed only when an input fails (`repl/session.go`); the stored warning is then printed again with every later compile error. Found 2026-11-16 auditing 87a01d1.
- Some messages name a line without saying which REPL input it is in: `import 'lib' (line 1) conflicts with the import 'lib' defined on line 1`, and `set by its first write, on line 2`. Since 87a01d1 a loader error in a file repeats its location (`already defined on line 1 of dup.qrk at dup.qrk:2:1`). Found 2026-11-16 auditing 87a01d1.
- `extern source` accepts any file. A header (`extern source 'std/io.hpp'`) is turned into a precompiled header by `clang -c` and cached as an object; the link then fails with `.../obj/<hash>.o: file format not recognized` and the "compiler bug" hint, and the bad object stays in the cache. A `.c` file is compiled as C++, so valid C fails with QK-FFI-003 (an amalgamated `sqlite3.c` wouldn't build). Found 2026-11-16 auditing 11df436 (`toolchain/sources.go`).
- Whether an `extern source` compiles depends on the precompiled header: a source that uses Quark types without `#include "quark/quark.hpp"` builds, because `-include-pch` brings in the runtime, and fails with QK-FFI-003 under `--no-pch` or when the precompiled header can't be used. Found 2026-11-16 auditing 11df436.
- Two `extern source` files that define the same non-inline symbol give a link error that names two hashed cache objects, both shown as `glue.cpp`, followed by the "compiler bug" hint. Found 2026-11-16 auditing 11df436.
- `quark run` of a program killed by a signal (a segmentation fault in glue code, for example) prints nothing and exits 255, and the program's buffered stdout is lost (`main.go`: `exitErr.ExitCode()` is -1 for a signal). Found 2026-11-16; older than the audited commits.
- Date range and zone errors name the wrong cause. `time::format(time::from_days(2147483647))` says `timestamp is not a finite time it can show`; `ts_from_date` of that date says `date is not a real calendar day`, and so does `ts_from_date(time::date(2018, 11, 4), true)` with `TZ=America/Sao_Paulo` (local midnight falls in a DST gap). Dates span about ±5.88 million years and every one of them parses (`time::ymd`, CSV), but `time::date(y, m, d)` rejects a year past ±999999 with `year is out of range`. `to_bool` of a date says to use `time::to_days` (`rejectDateConversion`, `types/analyzer_calls.go`). Found 2026-11-16 auditing dbc5789.
- Dates and periods print inconsistently: `print` shows year 1 as `0001-01-01` and `time::format` as `1-01-01` (`strftime`'s `%Y` isn't padded), and a negative period prints as `-1 months`. Found 2026-11-16 auditing dbc5789.
- Windows, found by reading the code on 2026-11-16 and not reproduced (no Windows machine): a `time::format` or `time::format_time` pattern with a conversion the Microsoft C runtime doesn't know (glibc's `%-d`, `%P`, `%k`, a trailing `%`) makes its `strftime` call the invalid-parameter handler, which by default ends the program with no Quark message; the runtime sets no handler (`q_time_strftime`, `src/core/stdlib/time.hpp`). If it returned instead, the 0 it gives would be taken for a short buffer, and the message would be `pattern produced no output, or more than 1MB of it`. Found while fixing `%s`, `%Z` and `%z` for UTC times.
- `qext::define_handle_kind` in a glue header that is both `extern 'hdr.hpp'`-included into the generated program and `#include`d from an `extern source` runs twice at startup and aborts with `error[QK-RUNTIME-001] (runtime): handle kind 'qffi.x' is already defined` (no Quark location). A `static const uint16_t KIND = qext::define_handle_kind(...)` at namespace scope in the header is one initializer per translation unit; with `extern source` there are two. The kind define belongs in the `.cpp` only (or a C++17 `inline` variable), but the message does not say that, and the same header worked when the glue was header-only. Found 2026-11-14 reviewing FFI phase 2 (P2+P3). Reach: adding `extern source` to an existing header that registered kinds makes a program that used to run fail at startup.
- A struct named like a builtin type is accepted, and the annotation then means the builtin: `struct int:` / `    x: int`, then `p: int = int { x: 1 }` is `cannot assign value of type 'int' to 'int'`, and `struct vec:` is a parse error (`expected struct name after 'struct'`). It should be a clear error at the `struct` (`'int' is a builtin type; choose another name`). Found 2026-11-13 while adding the `tbl` type (tables v0.1). Reach: `tbl` is now a builtin type name, so a program with `struct tbl:`, which worked before, now gets these messages where it uses `tbl` as an annotation. The `date` and `period` types (dbc5789) do the same to programs with `struct date:` or `struct period:`, which ran at `31abf4c`: `fn f(p: period) -> p.y` now fails with `argument 1 of 'f' expects period, got period`, and the changelog's Breaking section doesn't mention it.
- Two-argument `min` and `max` can't be used in a query: `mutate(m = max(e.mpg, 20.0))` says `the type of column 'm' isn't known; ... (annotate the return type of a function it calls)`, which a user can't do for a builtin. Their catalog entries return `any` (`builtins/catalog.go`), so even two floats give an untyped result; outside a query the value is checked later and works. Found 2026-11-16 probing queries for tables v0.3.
- A prelude builtin used as a value passes the checker and fails in clang: `f = len`, then `print(f('ab'))`, or `print(len)`, gives `use of undeclared identifier 'quark_len'`. Extern fns used as values work (they have thunks).
- `struct S` inside a `fn` body fails with `internal: struct 'S' not pre-declared`.
- A call written above a `fn` declaration is checked less than one below it. `print(apply(fn(a, b) -> a + b))` above `fn apply(k) -> k(1)` is a runtime error, below it a compile error.
- Calling a function value with more than 12 arguments compiles and always fails at runtime (`function call supports up to 12 arguments, got 13`); it could be a compile error.
- A struct field named with `__` (`a__b: int`) is accepted in the `struct` and rejected only where a literal uses it.
- Every lexer error after `=` is reported twice: `x = @` gives `unexpected character '@'` and then `unexpected '@' after '='; put each statement on its own line, or join the two with an operator`, and `x = 1__0` repeats the digit separator message inside a second one. The parser reports the `ILLEGAL` token as the expression error (`parseExpression`) and again when the statement doesn't end there (`endLine`, `parser/parser.go`). Found 2026-11-13 while adding digit separators (tables v0.1), whose error goes through the same path. Reach: digit separators add one more lexer error that hits it, and so does the unclosed-string error (2026-11-14): `x = 'abc` reports `unclosed string: ...` and then `unexpected 'unclosed string: ...' after '='`, and `print('abc)` adds `expected RPAR but got ILLEGAL`.
- A syntax error in an imported file is reported inside a load error located at the importer's `incl` line. Load errors in the main file show its absolute path, while check errors show the path as written. Several messages name token kinds instead of source text (`operator 'PLUS'`, `expected identifier after OK`, `no prefix parse function for NEWLINE`), and a multi-line `g = fn(x) ->` body gives about ten cascading `DEDENT` errors. Reach: the date operators (dbc5789) add `operator 'DIVIDE' is not defined for date and int`, and the same with `'MODULO'` and `'DOUBLESTAR'` (`temporalArith`).
- Native code that appends to a list with `push_back`, or writes `d->entries` directly, skips the element-type check; `qext::list_push` and `qext::dict_set` check it.
- `fmt::table(t)` shows a missing value as `NA`, while `print(t)` and vec printing show `null`: with a `tbl[Emp]` read from `id,salary` / `1,` / `2,5`, `print(t)` has `null` in the salary column and `fmt::table(t)` has `NA` (`q_fmt_vector_cells`, `stdlib/fmt.hpp`). Found 2026-11-14 adding table printing (tables v0.1). Reach: tables are now reachable from Quark, so `fmt::table` on one is too.
- Tooling: the `quark` package's integration tests take about 15 minutes on an idle 16-core machine (18.7 on a loaded one), past `go test`'s default 10-minute timeout, so the `go test -v` in CLAUDE.md's Build & Test Commands stops with `panic: test timed out after 10m0s`; pass `-timeout 60m` (the CI workflow does). Most of them compile and run a program one after another (5 call `t.Parallel()`). Found 2026-11-16.
- Tooling: the integration tests share one binary, `src/core/quark/quark_test`, which `TestMain` deletes at the start and end of every run. A second `go test` in the same checkout (another session, an editor) deletes it mid-run, and every integration test then fails with `fork/exec .../quark_test: no such file or directory`. Each run should build into its own temporary directory.
- A field read on a struct of unknown type that lacks the field says `dot access is only supported on dict; got type 'struct'` (`fn id(v) -> v`, `p = id(P { x: 1 })`, `p.y`).
- A wrong argument type for a fully annotated function or an `extern fn`, from an untyped value, reports `expected int, got str` without the function or parameter name (ordinary functions say `argument 'x' of 'f' expects int, got str`).
- Stdlib runtime errors use the old `.` spelling: `io::read` on a closed file says `io.read() expects an open file (resource is closed)`; `random.randint` and `blas.dot` likewise.
- `qext::box(int)` in native code doesn't compile (ambiguous between the `int64_t`, `double` and `bool` overloads); pass an `int64_t`.
- A program that imports `std/blas` starts OpenBLAS's thread pool (one thread per CPU), and then allocating large vecs makes the GC print `GC Warning: Repeated allocation of very large block (appr. size 78128 KiB): May lead to memory leak and poor performance` to stderr, and vec allocation gets erratic (`2.5 * a + b` on 10M-element vecs with `blas::axpy` measured 30 ms with `OPENBLAS_NUM_THREADS=1`, 135 ms without). The same program without `incl 'std/blas'`, or with `OPENBLAS_NUM_THREADS=1`, prints nothing (`src/benchmarks/RESULTS.md`).

## Slow paths and leaks

Times were measured on 2026-11-16, running the same program built at `31abf4c` and at `dbc5789` in alternation.

- `mutate(x = e.d + time::days(1))` is about 12× slower than `mutate(x = e.d + 1)` on 2M rows (0.10 s against 0.008 s), though `specs/dates_v0_1_spec.md` D5 and §7.4 say they are the same integer add: each row allocates a period and `q_date_add_period_raw` decodes and re-encodes the calendar date even when the period has no months or years. Found 2026-11-16 auditing dbc5789.
- A str column cell compared with a string literal still allocates the literal on every row: `filter(e.k == 'key7')` lowers to `q_sv_cmp_val(q_tbl_str_view(...), qv_string("key7"), "==")`, and `qv_string` copies the text (`core/constructors.hpp`), so it is only 4% faster than at `31abf4c`. When the other operand is a native `const char*`, the cell is boxed on every row. Found 2026-11-16 auditing tables v0.2 (65e9988).
- `random::sample(xs, k)` takes time and memory proportional to `len(xs)` whatever `k` is: it fills an index vector as long as `xs` (`src/core/stdlib/random.hpp`), so `sample(xs, 1)` on a 10M-element list costs about 100 ms a call. Found 2026-11-16 auditing 687a147.
- A whole-table float aggregate of an expression (`summarize(s = sum(e.a * e.b))`, and the same in `filter` and `mutate`) is computed by writing the expression into a temporary column and then running the column kernel. The bits match a column of those values. `specs/tables_v0_3_spec.md` §3.3 says to compute it in blocks along the pairwise split, with no temporary column. Found 2026-11-16 implementing tables v0.3 (`lower/query.go` `evalAgg`).
- A function call in a verb expression that doesn't read the row runs on every row anyway: `filter(c.mpg > mean(t.mpg))` computes the column's mean once per row, so the filter is quadratic (20K rows: 130 ms when this was `stats::mean(t.mpg)`, against 0.33 ms with `m = mean(t.mpg)` before the query and `filter(c.mpg > m)`; 1M rows would take minutes). Lowering emits the call inside the row loop (`lower/query.go`). `mean(c.mpg)` is now the aggregate and is computed once; this is the form that passes the column in from outside the row. Row-safety and computing such a call once per step are `specs/tables_v0_3_spec.md` D44, not implemented yet. Found 2026-11-16 looking at `stats::mean` in a query.
- Programs that include `std/time` or `std/sys` take 28 to 44% longer to compile than at `31abf4c` (`smoke_time_random` 2.7 s → 3.9 s; the `fib` benchmark 2.96 s → 4.04 s): both modules grew (687a147, dbc5789), and every function of an included module is emitted with its thunk whether the program calls it or not (about 860 more lines of C++ per program). A hello-world compile is about 13% slower. Found 2026-11-16.
- A build whose `extern source` object is already cached still runs `clang -M` over the source, without the precompiled header, before the main compile: about 380 ms per source that includes `quark.hpp` (a plain program builds in 1.6 s, the same with a cached source in 2.0 to 2.4 s). Found 2026-11-16 auditing 11df436 (`toolchain/sources.go`).
- Each `quark repl` input analyses every earlier input again and re-declares every earlier function in its C++, so input latency grows with the session: from about 0.4 s to 0.8 s by input 150 (28-line inputs), with the input's C++ growing from 7 KB to 32 KB. Found 2026-11-16 auditing 87a01d1.
- Closing unreachable files doesn't prevent running out of descriptors: a loop that opens files without closing them fails with `Too many open files` at `ulimit -n 1024` when the heap holds 3M live strings (the collector doesn't run often enough), and at 256, the macOS default, even with a small heap. A failed open could collect, run finalizers and retry. Found 2026-11-16 auditing 11df436.
- A handle whose GC payload refers to a child handle (a connection that remembers its statements) is never closed, and neither is the child: the registry slot is a root, and the payload → child → parent path keeps both reachable (`parent=1 child=1` still open after the last reference is dropped and four collections). Found 2026-11-16 auditing 11df436.
- The `extern source` object cache (`~/.cache/quark/obj/`) is never evicted, and the FFI integration tests write into the user's real cache under new keys on every run (`cleanEnv` keeps `HOME`). Found 2026-11-16 auditing 11df436.
- `quark repl` closed by SIGHUP (the terminal closes) or SIGTERM leaves its `/tmp/quark-repl-*` directory with every input's `.cpp`, `.o` and `.so`. Found 2026-11-16 auditing 87a01d1.

## Docs and tests that don't match the code

- The editor extension shows no hover documentation for most of `std/time`, and the wrong text for three functions: `time.qrk` (rewritten in dbc5789) has one comment per group of functions, and the editor data takes the comment just above a `fn` as its doc, so `days` shows `Calendar offsets. Adding one to a date rolls an impossible day back.`, `date` shows `Calendar day.`, and `timestamp` shows `Named timestamp, not time: a member can't share the module's name.`; `now`, `clock`, `ymd`, `format` and the rest show none (before the rewrite each had its own line). Found 2026-11-16 regenerating the editor data.
